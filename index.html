How it works

Every browser Stable Diffusion today (Web-SD, ONNX Runtime Web, Transformers.js) runs the denoising U-Net as dozens of kernel launches per step, times 20–50 steps. On consumer GPUs the launch overhead dominates — best-in-class browser SDXL Turbo is ~1 second on an RTX 4090. Nobody has broken the interactive barrier.

Our approach: collapse the sequential path.

text → tokens → CLIP embed (cached per prompt) → fused U-Net step × N → VAE decode (once per image) → canvas

The fused U-Net step is where the thesis lives: attention + GEMMs + GroupNorms + SiLU + residual adds collapsed into a single-digit number of dispatches per denoising step — vs. 60+ in ORT Web today. Diffusion is the textbook case where 1-dispatch fusion pays off, because the sequential step loop is launch-overhead-bound.

Roadmap

Shipped — fused kernels (v1.2). Hand-fused WGSL attention, FFN, and full transformer block at SD-Turbo shapes, benchmarked live above: 14 → 9 dispatches per block, correctness gated against the naive path. Plus fused GroupNorm, Conv, ResNet, cross-attention, and timestep embed as building blocks for our own U-Net.

Shipped — the product loop. ORT Web U-Net + our Euler scheduler generate real images on-device: as-you-type live preview, continuous morph mode, and a camera mirror (img2img). Models persist via the Cache API after the first ~2.5 GB download.

In progress — our WGSL U-Net (v2.5). Replace ORT's graph execution with our own dispatch loop over the fused blocks: ONNX parsed byte-level, weights straight into our kernels. Target: interactive latency (<100 ms per preview refresh) on mid-range consumer GPUs.

Next — shareable. URL-fragment-encoded prompt + seed + model + LoRA. Zero-backend sharing, same pattern as the .flora adapter format.
